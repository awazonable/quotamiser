# QuotaMiser 設計

要件は [`../requirements/requirements.md`](../requirements/requirements.md)。本書はそれを実装可能な形に落とす。要件が「何を守るか」を述べ、本書が「どう作るか」を述べる。

要件に書かれた制約を繰り返さない。本書が定めるのは、要件が「定める」とだけ述べた具体値と、要件が示した性質を成立させる機構である。

## 出発点

既存コードは無い。`openintelligence-labs/tokenmiser`（Rust、MIT）から**選択移植**する。fork しない。

| 移植する | 新規に書く |
| --- | --- |
| OpenAI 互換の HTTP 表面 | admission control 一式 |
| SSE の中継 | 予約台帳と精算 |
| provider アダプタの骨格 | 受理範囲の allowlist |
| ルータの骨格 | 安全入力の検証と安全ラッチ |

上流の budget 機構は移植しない。**事後記録・USD 建て・プロセス内メモリ**であり、本製品の**送信前・トークン建て・永続**な予約とは設計が別物である。移植時に上流の著作権表示と vendoring 元の commit SHA を `LICENSE` と `README.md` に記録する。

## 中核となる不変条件

本設計が守る性質は 1 つである。

```text
ある時点で上流に到達しうるすべてのリクエストの
最大消費量の総和 + 精算済み消費 <= 付与量
```

**台帳に記録された予約量ではなく、上流に到達しうる最大消費量**であることに注意する。この 2 つが食い違う設計は、台帳の上では不変条件を満たしたまま Pool を超える。

したがって**予約量は、そのリクエストが消費しうる最大量そのものでなければならない。** 軽量な推定値を予約し、より大きな上界で受理を判定する、という分離は成立しない。以下ではこの最大量を**負債（liability）**と呼ぶ。

## アーキテクチャ

```text
        client (OpenAI 互換)
              │
    ┌─────────▼──────────┐
    │ Ingress            │  正規化・allowlist・機能適合判定
    └─────────┬──────────┘
              │ 正規化済みリクエスト
    ┌─────────▼──────────┐      ┌──────────────────┐
    │ Admission          │◄────►│ Ledger           │  単一書き込み
    │  負債算定・予約      │      │  SQLite (WAL)    │
    └─────────┬──────────┘      └────────┬─────────┘
              │ 予約トークン                ▲
    ┌─────────▼──────────┐               │
    │ Dispatcher         │  取り消し耐性のある監督下で送信
    └──┬───────┬───────┬─┘               │
       │       │       │                 │
    ┌──▼──┐ ┌──▼───┐ ┌─▼────┐            │
    │OpenAI│ │Router│ │Local │  provider アダプタ
    └──┬──┘ └──────┘ └──────┘            │
       │                                 │
    ┌──▼─────────────────┐               │
    │ Settlement         │───────────────┘
    │  精算・回収ワーカー   │
    └────────────────────┘

    ┌──────────────┐ ┌──────────┐ ┌─────────────────┐
    │ Safety inputs│ │ Latches  │ │ Trusted clock   │
    │ 期限＋負債上限 │ │ 永続      │ │ 無課金の時刻取得 │
    └──────────────┘ └──────────┘ └─────────────────┘
```

### 所有権の境界

- **上流の HTTP クライアントと credential は Dispatcher モジュールの私有とする。** 他モジュールからクライアントを構成できない。予約トークンは複製不可能な型とし、**送信を開始する時点で消費する**（await した時点ではない）。型システムだけでは任意モジュールがクライアントを作るのを防げないため、可視性による封じ込めと組み合わせる。
- **Settlement のみが予約の負債を減らせる。** Ingress も Router も減らさない。
- **Ledger を書けるのは 1 プロセスのみ**（後述のロック）。
- **Safety inputs と Latches は Admission から読まれるが、Admission は書かない。**

## 負債の算定と受理

### 負債の定義

```text
liability = input_bound + output_bound
```

`output_bound` はクライアントが `max_output_tokens` を指定していればその値、なければモデルの最大出力トークン数。reasoning token を含む。

`input_bound` は次のいずれか。

**高速経路（構造的上界）** — リクエストが後述の**平坦なスカラ形**である場合に限る。

```text
input_bound = 本文の UTF-8 バイト長 + 書式トークン許容量 × 構造ノード数
```

バイト単位 BPE は基本語彙に 256 バイト値をすべて含み、マージは token 数を減らす方向にしか働かないため、`本文の tokens <= 本文の UTF-8 バイト長` が encoding によらず成立する。バイト長の算出は O(n) で、tokenizer を回すより安い。

**確定経路** — 上記以外はすべて `POST /v1/responses/input_tokens` で確定させ、返った値を `input_bound` とする。この endpoint は実測で無課金・無枠消費である。

### 高速経路の適用条件

高速経路は**平坦なスカラ形に限る**。具体的には、正規化後のリクエストが次の形であること。

- `input` が単一の文字列であること（配列でも構造化された content part の集合でもない）
- `instructions` が存在するなら単一の文字列であること
- `tools` が無いこと
- 添付・画像・ファイル・音声が無いこと
- モデルの encoding が明示表にあること

**この条件を満たさないものはすべて確定経路へ送る。** 「plain text」という曖昧な括りでは、1 個の最上位メッセージが数千の content part を含む形を高速経路に通してしまい、上流の書式トークンは part ごとに増えるため上界が破れる。構造ノード数を数えるより、**構造を持つものを高速経路から締め出すほうが安全で単純である。**

書式トークン許容量は `input_tokens` との突き合わせで測定し、観測値に対して大きく余裕を取った定数とする。平坦形ではノード数が 1〜2 に固定されるため、この定数の影響は小さい。

### 受理

```text
liability が残枠に収まるなら、liability を予約して送信する
収まらず、かつ高速経路だったなら、確定経路で input_bound を取り直して再判定する
確定値でも収まらないなら送信しない
```

**予約する量は liability そのものである。** 軽量な推定値は反実仮想の記録と TPM の先読みに使ってよいが、**在庫を左右してはならない**。

高速経路の上界は実トークン数の 3〜4 倍程度になるが、予約は在庫中のみ保持され精算で解放されるため、この保守性は累積しない。残枠が減ったときや入力が大きいときにだけ確定経路へ落ちる。

## 予約の状態機械

| 状態 | 上流に到達しうるか | 負債 |
| --- | --- | --- |
| `RESERVED` | いいえ | 計上 |
| `DISPATCHING` | **不明** | 計上 |
| `DISPATCHED_WITH_ID` | はい（`response.id` 既知） | 計上 |
| `DISPATCHED_ID_UNKNOWN` | はい（id 不明） | 計上 |
| `SETTLED` | 完了 | 実消費へ置換 |
| `CONSUMED_UNRECOVERABLE` | 完了 | 全額を消費として確定 |

**`DISPATCHING` は、リクエストを HTTP スタックへ渡しうるいかなる呼び出しよりも前に、永続化されていなければならない。**

これは async Rust では特に重要である。hyper の `send_request()` は返り値の future を構成する時点でリクエストを送信キューに積むため、**future を await する前に既にバイトが出ていきうる**。「await の順序」で守れる境界ではない。

送信は**取り消し耐性のある監督下**で実行する。タスクが drop されても、状態遷移だけは完了させる。

再起動時:

- `RESERVED` — 送信前に落ちたことが確実。負債を解放してよい。
- `DISPATCHING` — 送信したか不明。**保守側に倒し `DISPATCHED_ID_UNKNOWN` として扱う。**
- `DISPATCHED_WITH_ID` — 回収ワーカーに載せ直す。
- `DISPATCHED_ID_UNKNOWN` — 回収手段が無い。期限経過で確定する。

## 永続モデル

SQLite、WAL、`synchronous = FULL`、**`STRICT` テーブル**。

**設定の成否を検査する。** `PRAGMA journal_mode=WAL` は失敗しても以前のモードを返すため、戻り値を読まずに成功と見なすと、rollback journal のまま `FULL` の耐久性が保証されない状態で動きうる。起動時と**各書き込み接続で** `journal_mode=wal` と `synchronous=2` を照会して確認し、一致しなければ起動しない。ローカルの対応 VFS 上にあることも確認する。

```sql
CREATE TABLE pool_epoch (
    pool_id   TEXT    NOT NULL,
    epoch     INTEGER NOT NULL,
    granted   INTEGER NOT NULL CHECK (granted  >= 0),
    consumed  INTEGER NOT NULL CHECK (consumed >= 0),
    reserved  INTEGER NOT NULL CHECK (reserved >= 0),
    PRIMARY KEY (pool_id, epoch)
) STRICT;

CREATE TABLE reservation (
    id          TEXT PRIMARY KEY,
    root_id     TEXT    NOT NULL,   -- 引き継ぎ群の識別子
    pool_id     TEXT    NOT NULL,
    epoch       INTEGER NOT NULL,
    state       TEXT    NOT NULL CHECK (state IN
                  ('RESERVED','DISPATCHING','DISPATCHED_WITH_ID',
                   'DISPATCHED_ID_UNKNOWN','SETTLED','CONSUMED_UNRECOVERABLE')),
    liability   INTEGER NOT NULL CHECK (liability >= 0),
    settled     INTEGER,
    response_id TEXT,
    model       TEXT    NOT NULL,
    created_at  INTEGER NOT NULL,
    UNIQUE (root_id, epoch)          -- 引き継ぎの冪等性
) STRICT;
```

`UNIQUE (root_id, epoch)` が要である。ロールオーバがクラッシュ後に再実行されても、同じ群に対して同じエポックの負債が二重に作られない。

`safety_input` と `latch` も同様に `STRICT` で定義する。

算術は**検査付き整数演算**で行い、桁溢れや負値を黙って作らない。起動時の整合性検査で `reserved` を予約行から再計算し、`pool_epoch` の値と一致することを確認する。

### compare-and-reserve

```text
BEGIN IMMEDIATE
  ラッチを確認 → 立っていれば中止
  安全入力の期限と残り負債枠を確認 → 不足なら中止
  SELECT granted, consumed, reserved FROM pool_epoch WHERE pool_id=? AND epoch=?
  行が無ければ中止（暗黙に作らない）
  granted - consumed - reserved >= liability でなければ中止
  UPDATE pool_epoch SET reserved = reserved + liability
  INSERT INTO reservation (..., state='RESERVED', liability=?)
COMMIT
```

`BEGIN IMMEDIATE` で書き込みロックを即座に取り、読んでから書くまでに別の受理が入り込めない。**コミットの成功を確認してから次へ進む。結果が不確実なコミットは失敗として扱い、送信しない。**

### 終端遷移

**すべての終端遷移が在庫をどう動かすかを定義する。** 状態だけ変えて `reserved` を放置すると、負債が孤児になって Pool を殺す。逆に `reserved` を減らして `consumed` を増やさなければ、不明な枠を再オープンして課金を招く。

精算（群単位、冪等）:

```text
BEGIN IMMEDIATE
  root_id の全エポックの行を SELECT
  いずれも DISPATCHED_* でなければ何もせず COMMIT     -- 二重精算の防止
  各エポックについて:
    UPDATE pool_epoch SET reserved  = reserved  - liability,
                          consumed  = consumed  + actual
    UPDATE reservation SET state='SETTLED', settled=actual
COMMIT
```

回収不能の確定:

```text
BEGIN IMMEDIATE
  各エポックについて:
    UPDATE pool_epoch SET reserved = reserved - liability,
                          consumed = consumed + liability   -- 全額を消費とする
    UPDATE reservation SET state='CONSUMED_UNRECOVERABLE'
  必要ならラッチを同じトランザクションで立てる
COMMIT
```

**ラッチは、それを引き起こした精算と同一トランザクションで立てる。** 精算がコミットしてからラッチを立てる前にプロセスが死ぬと、次のプロセスがもう 1 件受理してしまう。

実消費が予約を超えていた場合は、**超えた実測値で精算する**（予約量に丸めない）。台帳は実際に消費された量を持つべきであり、同時に上限超過ラッチを立てる。

## 引き継ぎと群

エポックを跨いだ予約は、`root_id` を共有する複数行として表現される。

- ロールオーバは単一トランザクションで、未終端の各予約に対し新エポック行を `INSERT ... ON CONFLICT DO NOTHING` で作る。`UNIQUE (root_id, epoch)` により再実行しても増えない。
- **精算は群全体を 1 トランザクションで CAS する。** 片方のエポックだけ精算すると、もう片方の負債が永久に残る。
- 回収不能の確定も同じ群単位で行う。

## 巻き戻しの検出

**等値は信頼の証明にならない。** 台帳・局所 HWM・Usage API の 3 つが一致していても、スナップショットを取った後に送信し、その消費が Usage API に反映される前に復元すれば、すべて整合したまま在庫だけが復活する。

したがって次の 2 段構えとする。

1. **送信の前に、巻き戻し領域の外側へ単調増加する世代と累積負債を `fsync` して書く。** 置き場所は設定で指定し、**台帳とは別のボリュームを推奨する**。台帳ファイルだけの差し替え・破損・部分復元はこれで検出できる。
2. **Usage API を外部の権威として使い、ドリフトの検出にのみ用いる。** `ledger.consumed` が Usage API の報告値を下回っていれば巻き戻しである。ただし**下回っていないことは信頼の証明ではない**。

さらに、**清浄な停止マーカー**を持つ。マーカー無しで起動した場合は、整合していても `STATUS_UNKNOWN` へ入る。

**ホスト全体を巻き戻された場合、ローカルのどの手段でも検出できない。** これは設計上の残存リスクとして記録する。要件の「保証の対象外」にある「復旧後の台帳」がこれを含む。

Usage API の照会は、対象モデル群・エポック境界・ページングの完了・遅延の扱いを明示して実装する。「許容遅延を引く」という表現は単位が合わない（遅延は時間、消費はトークン）。**遅延窓の内側は判定に使わない**、と定義する。

## 時刻とロールオーバ

**課金も枠消費もしない時刻源を、推論の可否から独立に持つ。** `GET /v1/models` は無料で応答に `Date` ヘッダを含むため、これを用いる。推論経路が閉じていても時刻は取得できる。

- 現在のエポックを**永続化し、単調にのみ進める**。巻き戻さない。
- 境界は 00:00 UTC。これより早い設定を許さない。設定可能な範囲に安全な下限を強制する。
- **新鮮で信頼できる時刻が得られない場合、ロールオーバを行わない。** 前エポックのまま留まる（＝枠が開かない）。「一定時間待つ」は時計誤差の上界にならない。ホスト時計が 2 時間進んでいれば、15 分待っても 2 時間早く開く。
- 正方向スキューガードは 5 分。信頼できる時刻の不確かさがこれを超える場合は、その不確かさ分だけ広げる。
- 境界を跨いだ応答は、実消費を**両エポックに計上する**。

## ロック

**保護対象は台帳ファイルではなく、付与量を共有する資源である。** 同じ credential を別々の DB パスで動かした 2 プロセスは、別々のファイルロックを取り、それぞれが満額の Pool を見る。

- ロックの identity は**推論 credential または設定された組織/Pool 識別子から導出する**。ホスト全体で正規な位置に置く。
- **カーネルが保持する排他ロック**（advisory lock）を用いる。ファイルの存在や PID ではなく、**カーネルの所有権を権威とする**。プロセス死亡時に自動解放されるため、古いロックファイルで復旧不能になることがない。
- PID や起動時刻は診断用メタデータとしてのみ書く。

## 具体値

要件が「定める」とした項目の既定値。すべて設定可能とし、安全側の下限・上限を強制する。

| 項目 | 既定値 | 根拠 |
| --- | --- | --- |
| retrieve 再試行間隔 | 5s から指数バックオフ、上限 60s | cancel の確定は実測で約 90 秒 |
| 回収の escalation | 15 分 | 運用者への通知。**確定はしない** |
| 回収の打ち切り | 当該エポックが照合から利益を得られなくなるまで、または応答保持期限まで継続 | 15 分で確定すると、実消費 1k のリクエストを 128k の永久損失に変える。回収の継続は枠を減らさない |
| `DISPATCHED_ID_UNKNOWN` の確定 | 5 分 | 回収手段が無いので保持する意味がない |
| 未終端 background の上限 | 32（回収ワーカーの処理能力に基づく） | **枠の安全は負債が担う。** `granted / 128000` は小さなリクエストまで Large で単一化してしまい、要件が定めた「出力上限未指定のものが単一化する」を超えて制限する |
| 安全入力の TTL | data sharing / project 15 分、カタログ 24 時間 + 起動時、OpenRouter 15 分 | 下記の負債上限と併用する |
| スキューガード | 5 分（時刻の不確かさが大きければその分広げる） | 上流 `Date` との比較で補正する前提 |
| `STATUS_UNKNOWN` の再取得間隔 | 30 分 | 要件どおり |

### 安全入力は時間ではなく負債で区切る

TTL は経過時間を区切るだけで、**その間に失われうる金額を区切らない**。検証直後に project の opt-in が外されれば、次の 15 分で Pool 全部が課金されうる。

したがって各安全入力のスナップショットに、**前回検証以降に受理してよい負債の上限**を併せて持つ。時間か負債のいずれかが尽きたら再検証する。再検証が済むまで受理しない。

可変なモデル別名は避け、**不変のモデルスナップショットを優先する**。別名を使う場合、Pool 所属・最大出力・context 上限・tokenizer 同一性を版に束ねて扱い、受理前に一括で検証する。検証から送信までの競合は原理的に消せないので、残存リスクとして記録する。

## Provider アダプタ

共通に必要な能力は「このリクエストを受けられるかの判定」と「予約トークンを伴う送信」である。**トレイトの形は移植元を見てから決める。** 台帳の抽象化はしない（要件の非目標）。

- **OpenAI**: Responses API、`background: true`、`store: true`。予約・精算・回収の全機構が付く。
- **OpenRouter**: トークン台帳を持たない。RPM / RPD のカウンタのみ。`:free` と `openrouter/free` の完全一致 allowlist。402 は provider を閉じて次へ。
- **Local (FreeToken Desktop)**: 枠が無い。`GET /health` で `ok` / `loading` / `error` を判定し、`loading` は down として扱わない。**同時実行を自前で数え**、上限超過は送信前に拒否する（上流は 429 を返さずキューイングするため）。retrieve は試みない。

## 失敗時の挙動

要件の遷移表に加えて 1 つ。**provider を閉じる操作はラッチと同じ永続化を持つ。** 401 / 403 / 402 で閉じた provider は、プロセス再起動で自動的に開かない。安全機構の失敗として扱い、明示的な是正を要する。

429 や一時的な 5xx による退避は永続化しない。可用性の問題であって安全の問題ではない。

## テスト戦略

**壊れると金銭的被害が出る性質は「上流に到達しうる最大消費量の総和が付与量を超えない」の 1 点である。**

台帳に記録された値だけを検査するテストは、この設計の主要な欠陥をそのまま合格させる。実際、初稿の「U で受理し A で予約する」構造は、`consumed + reserved <= granted` を常に満たしたまま Pool を超えられた。

- **ゴースト変数を持つ property-based test。** 上流に到達しうる各リクエストの最大消費量をモデル側で追跡し、**送信の線形化点で**「精算済み消費 + 全未終端負債 <= 付与量」を表明する。台帳の値ではなくこのゴースト量を検査する。これが中核。
- **生成した履歴を実物の SQLite に対しても流す。** 抽象状態機械だけで済ませない。
- **障害注入**を、少なくとも次の点で行う。
  - `DISPATCHING` の永続化とバイト送出の間
  - 送信と `response.id` 取得の間
  - 精算コミットとラッチコミットの間
  - ロールオーバの途中と、その再実行
  - 各状態遷移での kill
- **巻き戻し**。DB・WAL・局所 HWM の各組み合わせでスナップショットを復元し、Usage API の遅延で隠れた直近消費を含めて検査する。
- **時刻**。時計の飛び、時刻源の喪失、上流 `Date` との乖離。
- **多重起動**。同一 credential・異なる DB パスの 2 プロセスが同時に受理しないこと。
- **SQLite の設定失敗**。`journal_mode` の設定が失敗したときに起動しないこと。
- **受理範囲の allowlist。** 拒否すべきフィールド・tool・サーバ側文脈参照・リモート URL・構造化 content part の各ケース。**ここが漏れると admission control を通らずに課金される。**
- 実 API に対する契約テストは CI から分離し、手動で実行する。`quotamiser-probes.ps1` が原型となる。

## 安全上の制約

- 予約トークンを伴わない送信経路を作れないよう、HTTP クライアントと credential を Dispatcher の私有とし、予約トークンを複製不可能な型として**送信開始時に消費する**。
- 受理範囲は allowlist であり、拡張時に「拒否リストへの追加漏れ」が起きない構造にする。
- credential は 2 種（推論用・Admin）。Admin key は Usage API 照会にのみ使い、推論経路から到達不能にする。
- ログに credential とプロンプト本文を残さない。トークン数と識別子のみを記録する。

## ADR

- **0001** tokenmiser を fork せず選択移植する（人間承認済み、`state.md` に記録あり）
- **0002** 切断時の精算を `background: true` + cancel で行う（同期ストリームでは retrieve できないという実測に基づき、当初判断を覆した）
- **0003** 予約量を負債（消費しうる最大量）そのものとし、高速経路を平坦なスカラ形に限定する（受理と予約に別の量を使う分離が不健全であることが設計レビューで判明したため）
