# ADR-0006: 処理前の同期拒否では予約を解放し、生成開始を否定できない結果では保持する

- Status: Accepted
- Date: 2026-09-11

## Context

Dispatcher は予約を `DISPATCHING` として永続化してから上流へ送る。上流が 2xx 以外を返したとき、その送信に対応する Daily Pool の予約をどう扱うかは、要件の遷移表から決まらなかった。遷移表は fallback するかどうかだけを定めている。

金銭的に最も安全なのは、2xx 以外をすべて「送信済み・id 不明」として保持し、期限で全額消費に確定することである。しかしこれは可用性を大きく損なう。tier 1 の TPM 制限による 429 のたびに、何も生成されていないのに予約（出力上限未指定なら最大 128,000）が消費扱いになる。Codex は失敗のたびに新しいリクエストで再試行するので、Pool はすぐに尽きる。

## Decision

- **作成リクエストそのものに対して、上流が同期的に 400・401・402・403・404・422・429 を返した場合、その送信の予約を解放する。** 台帳に終端状態 `REJECTED_BEFORE_PROCESSING` を設け、遷移元は `DISPATCHING` のみとする。
- **3xx・5xx・タイムアウト・転送途中の切断など、生成が開始されなかったことを確定できない結果では、予約を保持する。**
- **429 を受けた Provider に対して、Dispatcher は回避行動をとる。** 上流が示すリセット（`Retry-After`、`x-ratelimit-reset-*`）まで、その Provider へ送信しない。成功応答が残量 0 を報告した場合も、429 を待たずにリセットまで送信しない。

## Rationale

- background で発行した作成リクエストが同期的に 4xx を返したなら、応答オブジェクトは作られておらず、生成が走っている先が存在しない。解放しても、上流に到達しうる消費を見落とさない。
- 列挙したステータスは、検証・認証・支払い・存在しない endpoint・レート制限という、処理の前段での拒否である。
- 3xx は API が本来返さない応答であり、応答した相手が上流本体とは限らず、元の要求が転送されて処理された可能性を否定できない（[ADR-0005](0005-upstream-client-without-resend.md)）。5xx・タイムアウト・転送途中の切断では、上流が要求全体を受け取り処理を始めた可能性がある。実測でも、書き込み後に接続が切れた場合にサーバは要求全体を受け取っていた。
- 429 で予約を解放しても、リセット前に送り続ければ次の 429 を招くだけである。失敗のたびに再試行するクライアントと組み合わさると嵐になる。

## Alternatives considered

**2xx 以外をすべて保持する。** 最も保守的だが、429 のたびに最大 128,000 を失い、実用に耐えない。

**4xx をすべて解放する。** 405・409・413 のように、処理前の拒否であることが確立していないステータスまで含めてしまう。列挙に含めないものは保持する。

## Consequences

- 金銭的な安全は、「列挙したステータスが同期的に返った作成リクエストでは、生成が始まっていない」という前提に依存する。これは上流の仕様に基づく前提であり、実測で確かめたものではない。
- 429 の回避状態は Dispatcher のプロセス内にあり、再起動で失われる。再起動直後に 1 件の 429 を受けうる。
- 列挙外の 4xx は保持されるため、そのようなステータスが頻発すれば可用性を損なう。観測したうえで列挙の見直しを判断する。
