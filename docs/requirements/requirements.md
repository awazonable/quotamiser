# QuotaMiser 要件

## 目的

LLM API を OpenAI 互換 Proxy 経由で利用し、無料枠を最大限活用しつつ、**意図しない課金を確実に防止する**。

## 保証の範囲と限界

QuotaMiser の fail-closed 保証は無条件ではない。次の前提の上でのみ成立する。前提が崩れたときに黙って課金を許すのではなく、**検知して停止する**ことを設計の要件とする。

- **上流 Provider が、公開された usage 仕様と出力上限を遵守すること。**
  OpenAI の `max_output_tokens` は reasoning token を含む上限として文書化されている。しかし gpt-5.6 系で `usage.output_tokens` がこの上限を超えて報告され、その値がそのまま請求される不具合が報告されている（2026-07-11 報告、710 コール中 31 件、2026-08-06 時点で未解決）。QuotaMiser はこれを倍率マージンで吸収しない。上限超過を観測した時点で当該モデルを遮断し、記録する。
- **無料 Quota を消費する組織全体を QuotaMiser が専有すること。**
  Pool は API key 単位ではなく**組織単位**で共有される。同一組織の別 key・別プロセスが Pool を消費すれば、QuotaMiser の台帳は在庫を過大に見積もり、fail-closed が破れる。「key を専有する」だけでは不十分であり、**組織全体の専有、または Pool を消費する全経路が同一の台帳を通ること**が前提となる。
- **残枠を照会する手段が存在しないこと。** OpenAI は無料枠の残量を返す API を提供しない。`x-ratelimit-remaining-tokens` は RPM/TPM 用であり無料枠とは無関係である。したがってローカル台帳が唯一の在庫権威となる。

**遮断器は被害を限定する装置であって、初回の課金を防ぐ装置ではない。** `billing.payer` による停止も、上限超過の検知も、ドリフト検出も、すべて**最初の1件が課金された後**にしか作動しない。課金ゼロを担保するのは admission control と受理範囲の allowlist であり、遮断器はその失敗を有限に抑えるためのものである。この区別を曖昧にしない。

### 保証の対象外

次の3つは、設計上の欠陥ではなく**意図的に受け入れた残存リスク**である。「課金ゼロ」を無条件に主張しない。

1. **無料枠の資格（enrollment）が予告なく失効した場合の、最初の1リクエスト。**
   data sharing への opt-in は、complimentary tokens の付与対象であることの証明ではない。OpenAI は opt-in **かつ資格を満たす**組織に付与すると述べており、資格や enrollment 状態を機械可読に照会する公式 API は確認できていない。したがって「対象組織が complimentary daily tokens に enrolled 済みであること」は**起動時の設定前提**として要求する。失効は事後の usage / cost 監視でしか検知できず、その時点で 1 件分は課金されている。
2. **台帳を復旧した後の在庫。**
   後述の復旧手順は反映遅延を吸収するが、遅延を**証明的に**排除しない。復旧を経た台帳に対しては fail-closed を主張しない。
3. **高速経路の書式トークン許容量。**
   本文の符号化については `tokens <= UTF-8 バイト長` が証明された上界として成立するが、上流が付与する role 境界などの書式トークンは本文のバイト列に現れない。高速経路を平坦なスカラ形に限定することで構造ノード数を固定し、許容量を測定値に余裕を取って定めるが、これは証明ではない。

**v1 の保証は「上流が仕様通りに振る舞い、組織が専有され、資格が維持され、受理範囲が守られている限りにおいて fail-closed」である。** これ以上の保証は主張しない。

## 前提条件

- OpenAI organization の tier は **1**。Data Sharing に opt-in 済み。**組織全体を QuotaMiser が専有する。**
- **対象組織が complimentary daily tokens に enrolled 済みであること。** 機械検証は v1 の必須要件としない（照会手段が存在しないため）。設定上の前提として要求し、実 usage / cost の監視で事後に検知する。
- QuotaMiser は **2 種類の credential** を必要とする。推論用の API key と、Usage API 照会用の **Admin key**。
- 利用者は**単一テナント**。認証は行わず、loopback にのみ bind する。
- OpenRouter アカウントは **前払い（prepaid）専用**とし、**請求書払い・信用枠（credit line）を持たないこと**。**無入金・auto top-up 無効・BYOK 未設定**とする。残高が無ければ有料機能の課金は成立せず 402 となり、課金は「黙って発生する」のではなく「リクエストが失敗する」形に変わる。これはアカウント既定の plugin など、リクエスト検査では防げない経路に対する構造的な防壁である。
  **信用枠を持つアカウントではこの防壁は成立しない**（残高がマイナスでも処理が継続しうるため）。残高・BYOK・auto top-up は起動時および定期に再検証し、**検証できない場合は OpenRouter 経路を閉じる**。
- 最終退避先として **FreeToken Desktop**（OpenAI 互換、ローカル推論、課金・クォータ・認証なし）を常時起動しておく。

## 受理するリクエストの範囲

**deny-by-default の allowlist を全経路に適用する。** 課金経路は「列挙して塞ぐ」のではなく「許可したものだけ通す」。列挙型の禁止では、こちらが知らない課金機能を塞げない。

**allowlist は本書または本書が参照する正規の成果物に、バージョンを付して具体的に列挙する。**「未知のフィールドを拒否する」だけでは不十分である。標準フィールドであっても課金や消費量を左右するものは、明示的に許可されない限り拒否される。

### 全経路に共通

- 許可された endpoint、ボディフィールド、ヘッダを**列挙し、列挙外をすべて拒否する**。未知のフィールド、未知のネストフィールド、重複した JSON キーを拒否する。
- リクエストは**一度だけ解析し、正規化して再直列化したものを上流へ送る**。クライアントが送ったバイト列をそのまま転送しない。
- クライアントが付与した credential、organization / project 指定のヘッダを**除去する**。
- **サーバ側の文脈を参照するフィールドを拒否する。** 具体的には `previous_response_id`、`conversation`、`prompt`（テンプレート参照）。
  これらは Responses API の標準フィールドだが、**上流で展開される入力トークン量を送信前に確定できない**。可視トークンが 5 個のリクエストが、保存済みの 200,000 トークンの会話を参照しうる。ローカル推定は可視部分しか数えないため、予約を大きく超える入力が成立する。fail-closed と両立しないため v1 では拒否し、必要になった時点で（実体の凍結・版固定・厳密な preflight を伴う形で）将来対応する。
- **リモートの file / image URL 参照を拒否する。** 計測時と生成時で内容が差し替えられうるため。上流が参照実体を固定するか再取得するかは未確認であり、確認できるまでは拒否とする。インラインまたはアップロード済みの実体のみ受理する。

### OpenAI 経路

- **すべての built-in / hosted tool を拒否する。** `web_search`、`file_search`、`code_interpreter`、`image_generation`、hosted shell 等。**tool の利用は無料枠の対象外であり、トークン台帳を一切減らさないまま課金が発生する。** これは admission control が原理的に捕捉できない経路であるため、受理段階で塞ぐ以外にない。
- opt-in 済みの project と、許可された service tier を**固定して送る**。クライアントに選択させない。
- **`store` は常に `true` として送る。** クライアントの `store: false` は転送しない。転送すると retrieve による精算手段を失う。

### OpenRouter 経路

- 許可するモデルは **`:free` サフィックス付きの列挙された ID** および **`openrouter/free`** のみ。**完全一致で検証する**（`:free` の無いベア ID は別エントリの有料モデルであるため、前缀一致は危険）。`:free` 版が存在しないモデルは対象外とする。
- `:free` への **suffix 重ね掛けを拒否する**（`:online` / `:nitro` / `:floor` / `:exacto` / `:thinking` / `:extended`）。
- 次のフィールドを拒否する: `plugins`、`transforms`、`provider`、`models`、`fallbacks`、preset 指定、および `openrouter:web_search` / `openrouter:web_fetch` 等のサーバ側 tool。
- **OpenAI 標準の `web_search` tool type も拒否する。** OpenRouter がこれを課金対象のサーバ側 tool へ自動昇格させるため、素通しは課金に直結する。
- PDF / ファイル入力を拒否する（engine 未指定時に有料 OCR へ自動フォールバックするため）。
- **Guardrails をサーバ強制の防壁として設定する。** モデル allowlist を同内容で設定し、USD budget も設定する。**$0 は設定できないことを確認済み**であるため正の最小値を用いる。したがって Guardrails は「課金を不可能にする装置」ではなく「暴走時の被害を有限に抑える装置」である。課金ゼロは、前払い・無入金であることと allowlist が担う。

### 残存リスクとして記録する

- Free Models Router（`openrouter/free`）は、要求機能に合致する無料モデルが無い場合の挙動が文書化されていない。有料へ遷移しないという明示的な保証は無い。
- OpenRouter のアカウント既定 plugin と privacy 設定は、リクエスト検査では防げない。前払い・無入金であることが唯一の構造的防壁である。

## 稼働前提の継続検証

前提の成立は**期限付きの安全入力**として扱う。検証できない前提は、成立しているものとみなさない。

各安全入力について、**取得元・最大許容経過時間（TTL）・取得失敗時の挙動**を定める。**受理判定は、期限内の検証スナップショットに原子的に依存する。** 「起動時および定期的に検証する」とだけ書いた場合、1 日 1 回の照会でも要件を満たしてしまうため、これでは不十分である。

対象となる安全入力:

- **Data Sharing の有効性と、対象 project の opt-in 状態。** 所有者がいつでも opt-out でき、opt-out されても API は正常に応答し、usage も台帳と一致したまま**全トークンが課金される**。TTL 超過または取得失敗で **OpenAI 経路を閉じる**。
- **モデルの同一性と諸元。** Pool 所属、**最大出力トークン数**、context 上限、tokenizer の同一性を**版に束ねて**保持し、受理前に一括で検証する。モデル ID や alias が別の版へ移り最大出力が変われば、こちらは 128,000 を予約したまま上流が 200,000 を出力しうる（QuotaMiser は上限値を送らないため、上流はこちらの想定を知らない）。**不変のモデルスナップショットのみを受理する**か、諸元を版付きの安全入力として扱う。
- **OpenRouter アカウントの残高・BYOK・auto top-up。** 検証失敗で OpenRouter 経路を閉じる。
- **上限超過の不具合が未解決であるモデル。** 対象から外すか、別途証明された固い上限に対して予約する。

## 機能要件

### 無料 Quota の管理

- OpenAI の Data Sharing による無料 Quota（complimentary tokens）を最優先で利用する。
- 無料 Quota は**共有 Pool 単位**で管理する。Pool はモデル横断で共有され、組織単位でプールされる。tier 1 における粒度は次の通り。

  | Pool | 日次枠 | 対象モデル（抜粋） |
  | --- | --- | --- |
  | Large | 250,000 | `gpt-5.6-sol` ほか上位モデル群 |
  | Small | 2,500,000 | `gpt-5.6-terra`, `gpt-5.6-luna` ほか小型モデル群 |

- 対象モデルの一覧と Pool 所属は**設定として保持し、コードに埋め込まない**。モデルの追加・廃止が頻繁であるため（例: `o1` / `o3-mini` / `o4-mini` は 2026-10-23 に停止予定）。

#### 日次リセットとロールオーバ

- 日次リセットは **00:00 UTC** とする（公式 Help Center に明記、確認済み）。**これより早い境界を設定可能にしない。** 早い境界は上流がまだ前日である間に新しい Pool を開け、その差分が課金となる。遅い側への調整のみ許す。
- **単調増加する UTC エポックとして扱い、決して巻き戻さない。**
- **正方向のスキューガードを、具体的な大きさとともに定める。** ホスト時計が進んでいると枠を早開けするため、境界の判定には信頼できる時刻源を用い、それが得られない場合はガード幅を広げる。「スキューガードを設ける」とだけ書いてもガード幅が未定義では意味を持たない。
- ロールオーバ時、**未終端の予約をすべて新しいエポックへ shadow reserve として引き継いでから**、新しい日の受理を開始する。未終端の予約は「前日のドリフト負債」ではなく、いま現に消費されつつある枠であり、満額開始によって消してはならない。
- 確定済みの前日ドリフトは繰り越さない。翌日は満額で開始する。
- 帰属が判定できない境界跨ぎの応答は、実使用量を**両日の台帳に計上する**。

### Admission control（本製品の中核）

- リクエスト送信前に、input token・max output token・安全マージンから**最大消費量を保守的に見積もる**。
- 最大消費量が残 Quota を超える可能性がある場合、そのリクエストを**送信しない**。残枠に合わせて切り詰めて送ることはしない（残枠を超えたリクエストは部分的に無料枠が適用されるのではなく、全額が課金されるため）。
- 並列リクエストによる Quota 超過を防ぐため、**送信前に Quota を予約する**。
- 実際の token 使用量取得後、**予約量との差分を精算する**。

#### 原子性と一貫性

「予約する」「永続化する」だけでは過剰受理を防げない。次を要件とする。

- 残量の確認と予約は、**単一の線形化可能なトランザクション**で行う（compare-and-reserve）。読んでから書くまでの間に別の受理が入り込む余地を残さない。
- **予約が永続化され確定応答が返るまで、上流へ 1 バイトも送信しない。** 送信が先行すると、クラッシュ後に古い台帳が復元され、消費が記録から消える。
- 精算は**冪等な compare-and-set** とする。ストリーム完了ハンドラと retrieve ワーカーが同じ予約を二重に精算し、同じ差額を二度解放することを防ぐ。
- 予約の状態遷移と残量の増減は**同一トランザクションで更新する**。片方だけが永続化された状態を作らない。
- **単一書き込みプロセスのロックを持つ。** ロックが保護するのは台帳ファイルでも credential でもなく、**付与量を共有する資源（組織と Pool）**である。同一組織の別 credential は同じ Pool を消費するため、credential を鍵にすると 2 プロセスが別々のロックを取り、それぞれ満額の Pool を見る。
- **記憶域の結果が不確実な場合は送信しない。** 書き込みの成否が判らないまま送ることは、記録のない消費を作る。

#### 予約の状態

| 状態 | 意味 | 枠の扱い |
| --- | --- | --- |
| `RESERVED` | 送信前 | 差し引かれている |
| `DISPATCHED_WITH_ID` | 送信済みで `response.id` を取得済み | 差し引かれている。**retrieve による回収が可能** |
| `DISPATCHED_ID_UNKNOWN` | 送信したが `response.id` を取得できていない | 差し引かれている。**回収手段が無い** |
| `SETTLED` | 権威ある usage を取得し精算済み | 差額を解放 |
| `CONSUMED_UNRECOVERABLE` | 回収を打ち切り、予約全額を消費として確定 | 解放しない |

`DISPATCHED_WITH_ID` と `DISPATCHED_ID_UNKNOWN` を分けるのは、**再起動時の扱いが異なる**ためである。両者を区別せず「未精算の予約は再起動時に消費確定」とすると、`response.id` を永続化して再起動後も回収を続けるという要件と矛盾し、回収可能な予約まで捨てることになる。

- **再起動時**: `DISPATCHED_ID_UNKNOWN` は打ち切り期限の経過をもって `CONSUMED_UNRECOVERABLE` へ確定する。`DISPATCHED_WITH_ID` は**回収を再開する**。
- クライアント切断時は、予約を即座に消費確定させず、かつ利用可能枠からは**全額差し引いたまま**とする。権威ある usage を取得できた場合にのみ、後から差額を解放する。
- 同一 Provider への再試行には、**新しい予約を取得する**。前の予約は元の状態のまま保持する。
- 捨てた枠は未確定損失として記録する。

#### 精算の検証

終端応答が返っても、その usage を無条件に信用しない。**次を検証し、いずれかを満たさない場合は解放せず、保守側の状態へ遷移させる。**

- usage が存在し、整数であり、想定範囲に収まること。
- 応答のモデルと service tier が、予約時に想定したものと一致すること。
- Pool 消費量の算出式が一意に定まること（どのフィールドを合算するかを本書で確定させる）。

検証を通らない usage に対する遷移先を定義しないと、楽観的な実装は枠を解放して課金を招き、保守的な実装は Large の予約を無期限に滞留させる。**どちらも定義せずに実装に委ねてはならない。**

#### 見積り戦略

- 出力側は、クライアントが `max_output_tokens` を指定しない場合、**モデルの最大出力トークン数**を上界として見積もる。上限値を注入して送信することはしない。
- **reasoning token は通常の output token と同様に扱い、予約・精算する。** OpenAI の仕様上 reasoning token は output usage に含まれ output token として課金され、無料枠は対象トラフィックの input / output token に適用される。したがって reasoning token は無料枠の output 側を消費する。
  これは「reasoning が別料金で課金されない」という意味ではなく、**reasoning で使った分も無料枠を食う**という意味である。可視出力が 1,000 でも reasoning が 5,000 なら、output 側は約 6,000 として扱う必要がある。`max_output_tokens` は reasoning token を含む上限であるため、モデル最大出力を上界とする見積りはこれを既に含んでいる。
- **予約する量は、そのリクエストが消費しうる最大量そのもの（負債）でなければならない。** 軽量な推定値を予約し、より大きな上界で受理を判定する、という分離は成立しない。台帳の上では `消費 + 予約 <= 付与量` を満たしたまま、上流に到達しうる実際の負債の総和が付与量を超えうるためである。軽量な推定値は記録や TPM の先読みに用いてよいが、**在庫を左右してはならない**。
- 入力側の上界は次のいずれかで定める。
  - **平坦なスカラ形かつ encoding が既知**の場合: 構造的上界（本文の UTF-8 バイト長 + 書式トークン許容量）を用いる。バイト単位 BPE では `本文の tokens <= 本文の UTF-8 バイト長` が encoding によらず成立する。
  - **それ以外**（構造化された content part、tool schema、画像・ファイル、encoding が未知）: `POST /v1/responses/input_tokens` で確定させる。この endpoint は実測で無課金・無枠消費である。
- 「plain text」という曖昧な括りで高速経路を定義しない。**構造を持つものはすべて確定経路へ送る。** 1 個の最上位メッセージが多数の content part を含む形では、上流の書式トークンが part ごとに増え、上界が破れるためである。
- 書式トークン許容量は当て推量とせず、`input_tokens` との突き合わせで**測定した値**に余裕を取って定める。実行時の自己較正は v1 の必須要件としない。
- モデル ID から encoding への対応は**明示的な表を自前で持つ**。tokenizer ライブラリの前缀一致に依存しない。`gpt-5` という前缀キーは `gpt-5.6-sol` にも一致し、確認されていない encoding を黙って返すため。表に無いモデルはローカル推定を使わない。

#### 出力上限未指定時の同時実行（v1 の製品仕様）

クライアントが出力上限を指定しない場合、予約はモデルの最大出力（128,000）を含む。tier 1 の Large Pool は 250,000/日であるため、**この形のリクエストは Large モデルに対して同時 1 本までとなる**。これは v1 の仕様として明記する。隠れた劣化ではない。

正常に精算されれば予約は解放されるため、終日にわたって枠が滞留するわけではない。ただし当日の実消費が進み、残枠が 128,000 を下回った時点以降、**出力上限を指定しないリクエストは Large モデルに対して受理されなくなる**。

送信を拒否したリクエストは、**反実仮想を添えて記録する**（「出力上限を N に制限していれば通っていた」）。この仕様が実害を生んでいるかを、観測データに基づいて判断できるようにするため。

#### レート制限との関係

RPM / TPM は無料枠とは別個の制限であり、超過しても課金は発生しない（429 が返るのみ）。したがって admission control の対象ではなく、ルーティングと再試行の判断材料として扱う。

`POST /v1/responses` の応答は `x-ratelimit-*` ヘッダを返すことを実測で確認した（tier 1 / `gpt-5.6-terra` で 500 RPM、500,000 TPM）。これを読んで次の送信可否を先読みできる。TPM の消費は `max(max_output_tokens, 推定 input)` で事前予約されるため、**上限値を上流に送らない見積り戦略は TPM の消費を抑える方向にも働く**。

`POST /v1/responses/input_tokens` は `x-ratelimit-*` を返さない。この経路のレート制限は観測できない。

#### 台帳

- 予約台帳は**永続化する**。プロセス再起動をまたいで在庫を保つ。
- 台帳は**単調増加する世代番号**を持つ。あわせて、**巻き戻し領域の外側に独立して耐久する消費量の high-water mark を置く。**
  世代番号とチェックサムだけでは、**自己整合的な古いスナップショットの復元を検出できない**。世代 7・消費 10,000 の時点でスナップショットを取り、世代 100・消費 240,000 まで進んだ後にファイルシステムごと巻き戻すと、世代 7 の台帳もそのチェックサムも妥当であり、比較対象が残っていない。チェックサムは破損を検出するが、巻き戻しは検出しない。
- **Usage API は、通常運転において記録済み消費を増やすことしかできない。枠を再オープンしてはならない。** 反映遅延を「消費が無かった証拠」と解釈することは、それ自体が課金経路である。
  唯一の例外が次の復旧手順であり、これは**意図的に設けた例外**である。

#### 台帳が欠損・巻き戻された場合の復旧

台帳を信用できない状態（欠損、世代の飛び、high-water mark との矛盾）で起動したとき、当日消費量を 0 と仮定してはならない。次の手順を取る。

1. 状態を **`STATUS_UNKNOWN`** とする。この間、**OpenAI 経路は閉じる**（残量が不明なため送信できない）。他の Provider への退避は妨げない。
2. Usage API で当日消費量を取得する。
3. **約 30 分待って再取得する。**
4. 2 回の値が安定していれば、それを当日消費量として採用し、通常状態へ復帰する。
5. 値が安定しない、取得できない、ページングが不完全である場合は `STATUS_UNKNOWN` を維持する。

**この手順は前項の「枠を再オープンしない」規則に対する明示的な例外である。** 30 分の安定は、Usage API の反映遅延（1 分バケットが締めた後も数分間増え続ける）を吸収するためのものだが、**遅延を証明的に排除しない**。復旧時点で在庫中だった応答や、より長い遅延を持つ計上は、2 回の観測のどちらにも現れないまま後から出現しうる。

したがって前掲「保証の対象外」の通り、**復旧を経た台帳に対して fail-closed を主張しない**。次のリセットまで停止するより可用性を優先する判断として、この残存リスクを受け入れる。

#### 遅延照合と回収

次の 2 つの機構のみを設ける。個別に作り分けない。

1. **応答単位の retrieve** — `GET /v1/responses/{id}` により、切断された応答や未終端の予約について権威ある usage を取得し、精算・回収する。`response.id` は streaming の `response.created` 事象で取得しておく。

   **この経路を成立させるため、上流へのリクエストは `background: true`、`store: true` で発行する。** 同期ストリームを切断した応答は retrieve できず 404 となることを実測で確認した（対照実験により retrieve 機構自体は正常に機能することを確認済み）。background で発行した応答は切断後も retrieve でき、正確な usage を取得できる。

   クライアント切断時は `POST /v1/responses/{id}/cancel` で生成を停止する。停止しなければ、誰も読まない出力のために枠を消費し続けるため。cancel した応答は**終端状態への確定に時間がかかる**（実測で約 90 秒）。確定までの間、`in_progress` 等の非終端状態が観測されるが、**これを「消費が無かった」と解釈してはならない**。終端状態に達するまで予約は差し引いたまま保持する。

2. **Pool 総量の遅延照合** — Usage API により、台帳の総量と実消費の乖離を検出する。

**この 2 つは役割が異なり、混同してはならない。** Usage API は Pool 総量の遅延照合であって、個別の未終端予約を精算する装置ではない。とくに、**Usage API に反映されていないことを根拠に未終端の予約を解放してはならない。**

乖離を検出した場合は記録して警告する。翌日の枠は満額で開始し、確定済みドリフトを負債として繰り越さない。

#### 精算待ちのあいだの可用性

「非終端を消費なしと解釈しない」は金銭的な安全のために必要だが、それ自体は可用性の設計ではない。約 90 秒の確定待ちのあいだ予約は差し引かれたままであり、出力上限未指定の Large リクエストであれば、その 1 件が同形のリクエストすべてを塞ぐ。切断が多い環境では、この閉塞が常態化しうる。

したがって次を要件とする。**いずれも具体的な値を定める。「定める」とだけ書いて実装に委ねない。**

- `response.id` と cancel の進行状態を**永続化する**。プロセス再起動をまたいで回収を継続できるようにする。
- retrieve の一時的な失敗は**再試行する。即座に消費確定へ倒さない**。再試行間隔と回数を定める。
- 一定時間で回収できない予約は**運用者に通知する**。ただし**通知は確定ではない**。短い期限で `CONSUMED_UNRECOVERABLE` に倒すと、実消費 1,000 のリクエストを予約全額（最大 128,000）の永久損失に変える。**確定を早めても枠は戻らない**（予約は全額差し引かれたままである）ため、早期確定に利益は無い。
- **回収は、当該エポックが照合から利益を得られなくなるまで、または上流の応答保持期限まで継続する。** `store: true` の応答は最低 30 日保持されるため、保持期限は実質的な制約にならない。
- `response.id` を取得できていない予約は回収手段が無いため、短い期限で確定してよい。
- **未終端の background リクエスト数に上限**を設け、超えたら受理しない。
- この背圧を**運用上観測できる形で外部に出す**。

### Fallback

無料の範囲でのみ連鎖する。

```text
OpenAI 無料 Quota  →  OpenRouter 無料モデル  →  Local LLM (FreeToken Desktop)
```

#### 遷移条件

**HTTP ステータスを一括りにしない。** 「400 系はクライアントに返す」という粗い規則は、こちらの安全設計が生む 402 を誤って処理する。

| 事象 | 挙動 |
| --- | --- |
| 枠不足（送信前の自己判断） | 次の Provider へ |
| 400 / 422（リクエスト不正） | fallback せずクライアントに返す |
| 401 / 403 | **設定または安全機構の失敗**として当該 Provider を閉じ、次の Provider へ。記録して警告する |
| 402（支払い要求） | **当該 Provider を閉じ、次の Provider へ。** OpenRouter を無入金にする設計はこの応答を意図的に生むものであり、クライアントへのエラーとして返してはならない |
| 3xx（リダイレクト） | **追従しない。** 経路または設定の異常として当該 Provider を閉じ（永続）、次の Provider へ。3xx を返した相手が上流本体である保証は無いため、予約は送信済みとして保持する |
| 429 | 次の Provider へ |
| 送信後の timeout / connection failure / 曖昧な 5xx | 予約を未終端のまま保持し、次の Provider へ |

- streaming で本文の送出が開始された後の失敗は fallback しない。クライアントが既に部分応答を受け取っているため。
- すべての Provider が利用できない場合、**エラーを返す**。次のリセットまで待機・キューイングしない。
- エラーボディには、次にどの Provider がいつ利用可能になるかを機械可読な形で含める。**ETA を提示できない Provider に対しては `unknown` を許す。** 提示できないことを、提示できるふりで埋めない。

#### 機能適合性による事前判定

Provider ごとに**対応機能の表**を保持し、ルーティング前にそのリクエストを処理できるか判定する。処理できない Provider は最初から候補から外す。

対応していない機能を送って 400 を得る方式は採らない。クライアントのリクエストが本当に不正な場合と区別できず、無駄な送信で枠を消費するため。この判定は送信前に完結するので Quota を消費しない。

既知の非対応例: FreeToken Desktop は `response_format` の json_object / json_schema、`logit_bias`、`function_call`、embeddings に対応しない。

### Local LLM

- FreeToken Desktop の OpenAI 互換 endpoint を利用する（既定 `127.0.0.1:1919`）。
- **モデルはサーバ起動時の設定で固定され、リクエストボディの `model` では選択できない。** リクエストの `model` は検証されずエコーされるのみで、存在しないモデル ID を送っても既にロードされているモデルが黙って応答する。
  したがって環境変数の役割は「モデルを選ぶ」ことではなく「**期待するモデルを宣言する**」ことである。QuotaMiser は起動時に `/v1/models` を読み、宣言と一致しなければ**起動を失敗させる**。
- 到達性は `GET /health` で判定する。`ok` / `loading` / `error` を区別できるため、**「落ちている」と「起動中で重みを読んでいる」を混同しない**。ロード中は長時間かかるため、down として扱わない。
- **同時実行の超過は拒否ではなくキューイングされる。** 429 は返らないため、過負荷を上流の信号から知ることはできない。したがって **QuotaMiser 側で同時実行数を管理し、上限を超えるなら送信前に拒否する**。あわせて**上限を定めたタイムアウト**を置き、それを超えたら利用不能と判断する。
- `/v1/responses` はステートレスな部分実装であり、`store` は黙って無視され `GET /v1/responses/{id}` は常に 404 を返す。**ローカルに対して retrieve を試みない。** ローカルには枠が無いため遅延精算も不要である。

### インタフェース

- OpenAI 互換 API として既存アプリから透過的に利用できる。
- **v1 の受け口は Responses API（`POST /v1/responses`）とする。** 想定する利用元は Codex CLI と、OpenClaw をフォークして作るエージェントである。Chat Completions の受け口は、後から変換アダプタとして追加しうる。上流と同じ形の受け口を先に作るのは、精算に関わる SSE の解析に形式の変換を挟まないためである。
- 上流には **Responses API** を用い、**`background: true`、`store: true` で発行する**。今後の OpenAI API との整合性、および切断後も `GET /v1/responses/{id}` で精算できる経路を確保するため。クライアントへの streaming は background 応答のストリームを中継する形で提供する。
- 応答には**処理を担当した Provider とモデルをヘッダで返す**。ボディの OpenAI 互換形式は変更しない。退避が起きたことを呼び出し側が観測できないと、品質低下の原因が追えないため。

### 停止条件と安全ラッチ

`billing.payer` が `developer` を返した場合（＝無料のはずのリクエストが課金された直接の証拠）、OpenAI 経路を停止する。この項目は文書化されていない best-effort な telemetry であり、失われた場合は停止条件が無効になるだけとする。

**停止はエポックをまたいで永続する安全ラッチとする。** 日次ロールオーバで自動的に解除してはならない。解除には**明示的な是正操作と、破られた不変条件の再検証**を要求する。日付が変わっただけで満額の Pool が開けば、原因が残ったまま翌日も最初の 1 件が課金され、それが毎日続く。

この停止条件は**課金の防止ではなく、課金の連鎖の遮断**である。前掲「保証の範囲と限界」の通り、遮断器は初回の課金を防がない。

## 制約

- **v1 では有料 API を利用するモードそのものを実装しない。** 設定でも、ヘッダでも、有料経路は存在しない。
- 将来必要になった場合は、日次の soft / hard budget を持つ経路として追加しうる。その場合も「許可すれば無制限」にはしない。

## モデル指定時のルーティング（補助要件）

モデル指定アクセスは、可能な範囲で指定モデルを優先する。

| 指定されたモデル | ルーティング |
| --- | --- |
| Data Sharing 対象の OpenAI モデル | 当日の無料 Quota に余裕があれば指定モデルへ送信 → 利用できなければ無料 Fallback へ |
| Data Sharing 対象外の OpenAI モデル | **Small Pool 内で要求に見合う最上位モデル**（既定 `gpt-5.6-terra`） → その他の無料 API → Local LLM |
| 無料 API 系モデル | 指定された無料 API/モデル → 利用不能時は Local LLM |

退避先を固有名ではなく「Small Pool 内の最上位」という規則で表現するのは、モデルの世代交代に追従するためである。既定を `gpt-5.6-terra` とするのは、`gpt-5.6-sol` が Large Pool（tier 1 で 250,000/日）に属するのに対し、terra が Small Pool（同 2,500,000/日）に属し、**10 倍の無料枠を持つ**ためである。

このルーティングは**補助要件**とし、**無料枠超過防止を最優先**する。

## 非目標

- 有料 API のコスト最適化（安い有料モデルへの誘導）は目的ではない。有料は既定で禁止であり、最適化の対象ですらない。
- 汎用的なマルチプロバイダ・ゲートウェイを目指さない。無料枠を守り切ることに範囲を絞る。
- 予約台帳の共通抽象化は行わない。Provider ごとに資源の次元が異なるため（OpenAI はトークン、OpenRouter はリクエスト数、Local は無制限）、台帳は Provider ごとに個別に持つ。fail-closed な admission control が必要なのは OpenAI 経路のみである。
- マルチテナント、公平性制御、認証は v1 の範囲外とする。
- サーバ側の会話状態（`previous_response_id` / `conversation` / `prompt`）への対応は v1 の範囲外とする。

## 実測で決着した事項

2026-09-09 に本番 key で実測。tier 1、`gpt-5.6-terra`。

| 項目 | 結果 |
| --- | --- |
| 同期 stream を切断した応答の retrieve | **404**。取得できない。（対照として、通常完了した応答は retrieve 可能であることを確認済み） |
| `background: true` で発行した応答を切断 | 生成は継続し完了。**正確な usage を取得できた** |
| `background` + 切断 + `cancel` | 生成は即停止。**約 90 秒後に `status=cancelled` と正確な usage が確定**。確定前は非終端状態が観測される |
| `output_tokens <= max_output_tokens` | 20 件中**違反ゼロ**。上限到達時は `status=incomplete` で正しく停止 |
| `POST /v1/responses/input_tokens` | 100 件中失敗ゼロ。**`x-ratelimit-*` ヘッダは返らない**。`input_tokens` は正確な整数を返す |
| `POST /v1/responses` の `x-ratelimit-*` | **返る**。tier 1 / terra で 500 RPM、500,000 TPM。TPM の事前読みが可能 |
| OpenRouter Guardrails の $0 budget | **設定できない**。正の最小値を用いる必要がある |
| `input_tokens` 100 件の課金 | 翌日確認して当日 cost は **$0**。Usage API の completions にも計上されず（計上されていれば input が約 9,400 増えるはずだが 1,922 だった）。**課金されず、無料枠も消費しないと判断する** |
| 当日の総消費（実測日） | terra で in=1,922 / out=72,644 / 23 リクエスト、cost **$0**。無料枠が実際に適用されていることの確認になる |
| reasoning token が無料枠を消費するか | out=72,644 のうち 2 万トークン超が reasoning であり、それを含めて cost **$0**。**reasoning token は無料枠で賄われている**。公式文書の合成（reasoning token は output usage に含まれ output token として課金される／無料枠は対象トラフィックの input・output token に適用される）とも一致する |

`input_tokens` の判定には留保がある。照会したのは Usage API の completions であり、この endpoint が `input_tokens` 経路を含む保証は無い。したがって「usage に現れない」ことは消費ゼロの証明ではない。ただし**課金が発生しなかったことは確定**しており、無料枠を消費するならその消費がどこかに記録されるはずである以上、現時点で得られる最良の証拠として扱う。

`output_tokens` の検証は 20 件である。報告されている不具合の発生率は 4.4%（710 件中 31 件）であり、**20 件では見逃しうる**。この結果は「前提が成立することの確認」ではなく「反証が得られなかった」に留まる。回路遮断の実装は依然として必要である。
