# ADR-0003: 予約量は負債そのものとし、高速経路を平坦なスカラ形に限定する

- Status: Accepted
- Date: 2026-09-10

## Context

入力トークン数を送信前に知る方法は 2 つある。ローカルで数える（速いが正確とは限らない）か、`POST /v1/responses/input_tokens` で確定させる（正確だが往復が増える）。

軽量性を優先する方針から、当初の設計は次の分離を採った。

- **予約量** = 軽量なローカル推定 + 測定した安全マージン
- **受理の可否** = より保守的な構造的上界（UTF-8 バイト長）

「推定が外れても実消費は上界以下なので Pool を超えない」と考えたが、これは誤りだった。

## Decision

**予約量は、そのリクエストが消費しうる最大量（負債）そのものとする。** 軽量な推定値は反実仮想の記録と TPM の先読みに用いてよいが、在庫を左右してはならない。

**高速経路は平坦なスカラ形に限定する。** `input` が単一文字列、`instructions` があれば単一文字列、tools 無し、添付無し、encoding が既知。これを満たさないものはすべて `input_tokens` で確定させる。

高速経路の上界は、`input` と `instructions` の**両方**を含む正規化後の全対象文字列の UTF-8 バイト長の合計に、書式トークン許容量を加えたものとする。

## Rationale

**分離は不健全である。** 台帳の残量は予約量から計算されるため、上界 100,000・予約 20,000 のリクエストは残量を 20,000 しか減らさない。250,000 の Pool に 3 本通せば、台帳上は `consumed + reserved <= granted` を満たしたまま、実際の負債の総和は 300,000 になる。

精算の代数でも同じことが見える。精算後は `C' + R' = C + R + (actual − A)` であり、`actual > A` なら**送信済みのリクエストが不変条件を事後に破る**。`BEGIN IMMEDIATE` は誤った会計を直列化するだけで、耐久性設定はそれを確実に永続化するだけである。

したがって守るべき不変条件は台帳の値についてではなく、**上流に到達しうる最大消費量**について述べられなければならない。

高速経路の限定については、「plain text」という括りが上界を保証しないためである。1 個の最上位メッセージが多数の content part を含む形では、上流の書式トークンが part ごとに増える。構造ノードごとの上界を証明するより、**構造を持つものを高速経路から締め出すほうが安全で単純である。**

## Alternatives considered

**軽量推定を上界として使う。** マージンを上界と見なせば分離は消えるが、統計的に測定したマージンには保証された誤差帯が無い。残枠が推定値と等しいとき、1 トークンの過小評価でリクエスト全体が課金されうる。

**常に `input_tokens` を使う。** 最も正確で単純だが、すべてのリクエストに往復が増える。実測でこの endpoint は無課金・無枠消費と判明しているため実行可能ではあるが、軽量性の要求に反する。

**構造ノードごとの書式トークン上界を証明する。** 高速経路を広く保てるが、上流のスキーマが公開されておらず、モデル版ごとに証明を維持する必要がある。得られる範囲に対して負担が大きい。

## Consequences

- 高速経路の上界は実トークン数の 3〜4 倍程度になる。予約は在庫中のみ保持され精算で解放されるため、この保守性は累積しない。残枠が減ったときや入力が大きいときにだけ確定経路へ落ちる。
- 確定経路に落ちる頻度は、当初の設計より高くなる。`input_tokens` が無課金であることが実測で確認されているため、これは許容できる。
- 書式トークン許容量は測定して定める必要がある（未実施）。**この部分は証明された上界ではない**ため、要件の「保証の対象外」に残存リスクとして記録している。
- テストは台帳の値ではなく、上流に到達しうる最大消費量をゴースト変数で追跡して検査しなければならない。台帳の値だけを見る property test は、この ADR が退けた欠陥をそのまま合格させる。
