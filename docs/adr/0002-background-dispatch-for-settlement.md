# ADR-0002: 上流へは `background: true` で送り、切断時は cancel して精算する

- Status: Accepted
- Date: 2026-09-10

## Context

クライアントが streaming の途中で切断したとき、その予約をどう精算するかを決める必要がある。切断時に usage を報告する終端チャンクは届かない可能性があり、届かなければ実消費が分からない。

分からないまま予約を解放すれば fail-closed が破れる。解放しなければ、予約全額（出力上限未指定なら最大 128,000 トークン）を失う。tier 1 の Large Pool は 250,000/日なので、切断 1 回で半分を失いうる。

当初は「同期ストリームで送り、切断後に `GET /v1/responses/{id}` で権威ある usage を取得する。取得できなければ全額消費として確定する」と決めていた。この前提が成り立つかは文書からは判断できなかった。

## Decision

**上流へのリクエストは `background: true`、`store: true` で発行する。クライアント切断時は `POST /v1/responses/{id}/cancel` で生成を停止し、`GET /v1/responses/{id}` で権威ある usage を取得して精算する。**

クライアントへの streaming は background 応答のストリームを中継する形で提供する。

## Rationale

2026-09-09 に本番アカウント（tier 1、`gpt-5.6-terra`）で実測した。

| 方式 | 切断後の retrieve | usage | 生成 |
| --- | --- | --- | --- |
| 同期 stream + 切断 | **404** | 取得できない | 停止 |
| `background: true` + 切断 | 成功 | 正確に取得（out=2,571） | 完了まで継続 |
| `background` + 切断 + `cancel` | 成功（約 90 秒後に確定） | 正確に取得（out=5,337） | **即停止** |

対照として、通常完了した応答は retrieve できることを確認した。つまり retrieve 機構自体は正常で、**中断された同期ストリームの応答だけが取得できない**。

したがって当初の前提は成り立たない。cancel を伴う background だけが、生成の浪費を止めつつ正確な精算を可能にする。

## Alternatives considered

**同期ストリームのまま、切断時は予約全額を消費として確定する。** 実測後に残った唯一の代替。実装は単純だが、切断 1 回で Large Pool の半分を失う。切断の多い環境では実用に耐えない。

**`background` を使うが cancel しない。** 精算はできるが、誰も読まない出力のために枠を消費し続ける。実測でも切断後に生成が完了していた。

## Consequences

- **精算が遅延する。** cancel した応答が終端状態に達するまで実測で約 90 秒かかる。その間、予約は差し引かれたまま保持される。確定前には `in_progress` などの非終端状態が観測されるが、**これを「消費が無かった」と解釈してはならない。**
- 出力上限未指定の Large リクエストでは、この 90 秒が同形のリクエストすべてを塞ぐ。可用性の設計（回収の永続化、再試行、未終端数の上限、背圧の可視化）が別途必要になる。
- `store: true` が前提となるため、クライアントの `store: false` を転送できない。
- background モードには不具合の報告がある（接続直後の切断で `queued` から復帰しないなど）。実測では再現せず、cancel 直後の非終端状態は約 90 秒で解消した。継続的な観測が必要である。
